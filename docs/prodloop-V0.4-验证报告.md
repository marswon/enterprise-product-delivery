# prodloop V0.4 业务 UI 模块验证报告

验证日期：2026-09-02

## 本次目标

把企业业务系统的界面设计与验收纳入 `prodloop` 原有交付状态机，解决仅凭营销站视觉参考生成后台页面、组件库混用、复杂状态缺失和截图代替可用性验收的问题。

## 实现范围

- 新增业务 UI 模式路由，覆盖通用中文后台、ERP、CRM、数据控制台、工业运维和高可访问性数据应用。
- 新增视觉参考规则，将 `awesome-design-md` 定位为可选视觉语言来源，而不是产品交互或实现底座。
- 明确产品结构、业务交互模式和视觉语言三层顺序。
- 要求每个界面只采用一个主要实现系统；已有项目优先复用当前组件和设计系统。
- 状态 schema 升级为 V3，新增 `interface_scope`。
- 初始化创建 `UI_CONTRACT.md` 和 `UI_VERIFICATION.md`。
- 旧 V1/V2 状态可非破坏性启用 UI 门禁；升级前保留状态与 manifest 备份，不覆盖已有 UI 产物。
- G0 拒绝未明确的界面范围；界面在范围内时，G3 拒绝不完整 UI 合同，G6 拒绝不完整 UI 验收。
- S6 要求真实浏览器、真实任务、代表性数据、角色、异常状态、响应式和可访问性证据；截图不能替代交互。

## 来源边界

模式路由链接到 Ant Design/Ant Design Pro、SAP Fiori/UI5、Cloudscape、Salesforce Lightning、PatternFly、Carbon 和 TDesign 的官方资源。V0.4 没有复制这些项目的组件代码、品牌资产、专有字体或完整文档。

第三方仓库许可证不自动授予商标、专有字体、插画或独特品牌身份的使用权。实际项目采用代码前仍需核对当时的维护状态、许可证、技术栈和现有系统约束。

## 证据边界

- 结构和状态门禁可以阻止跳过产物，但不能自动证明产物内容正确。
- 官方设计系统提供参考，不代替当前产品用户研究、业务规则和真实任务观察。
- V0.4 尚未在三个不同类型的真实业务仓库完成前向测试，不声称已证明能够自动产生优秀 UI。
- 第一次真实使用应优先选择一个范围明确的已有业务流程，记录设计返工次数、关键任务缺陷、浏览器验收缺陷和人工干预点。
- 官方 `quick_validate.py` 仍因当前 Python 环境缺少 `PyYAML` 无法执行；本次使用 Ruby YAML 解析器校验 frontmatter，并另行执行行为测试和语法编译。
