# 企业级 AI 自主产品交付系统规格 V0.1

> Skill 名称：`prodloop`
>
> 文档性质：Skill 实现前的系统规格。它定义交付状态机、质量门禁、权限边界和证据协议，不代表 Skill 已经实现或任何产品已经完成开发。

> V0.3 兼容说明：为支持 Codex 与 Kimi Code 共用，当前实现默认使用 `.prodloop/`，并自动识别 V0.1 的 `.codex/delivery/`。V0.3 进一步区分 `greenfield` 与 `brownfield` 项目上下文，并为老项目增加接管门禁。本文件其余 `.codex/delivery/` 内容保留为 V0.1 历史规格，不应覆盖当前实现约定。

## 1. 目标

建立一套可复用于新产品、已有系统功能开发、企业流程改造、系统集成和迁移项目的 AI 产品交付系统，使 AI 能够在已授权边界内，从模糊目标开始，连续完成：

`调查分析 -> 产品定义 -> 产品与交互设计 -> 技术设计 -> 交付规划 -> 开发集成 -> 独立验收 -> 发布准备 -> 结果观察`

系统追求的不是“无人提问”，而是“无人日常调度”：人只负责业务目标、重大决策和高风险授权；AI 负责可以通过证据、规则和可逆操作自行推进的工作。

### 1.1 成功定义

一次交付只有同时满足以下五类结果才算完成：

1. **产品正确**：解决了已定义用户在已定义场景中的问题。
2. **体验可用**：关键任务能在真实界面或真实接口中顺利完成。
3. **工程可靠**：代码、数据、权限、异常和兼容性达到所选质量档位。
4. **可以发布**：具备迁移、监控、恢复、回滚和运维证据。
5. **能够学习**：上线后可以观察结果，并判断继续、调整或停止。

### 1.2 非目标

- 不用一套固定技术栈覆盖所有项目。
- 不把文档数量、代码行数、测试数量或 AI 自述当作完成证据。
- 不让 AI 在缺少事实时自行编造用户需求、业务规则或成功指标。
- 不默认授权生产发布、删除数据、修改权限、产生费用或联系外部人员。
- 不用原型质量冒充企业生产质量。
- 不替代特定领域的法规、安全、财务、医疗或行业专业审查。

## 2. 核心模型

系统由三套相互制约的子系统组成。

### 2.1 决策系统

回答“为什么做、给谁做、做到什么程度”：

- 目标用户与关键场景；
- 当前问题及证据；
- 业务目标与成功指标；
- 范围、非目标和优先级；
- 可由 AI 代为决定的事项；
- 必须由产品责任人裁决的事项。

### 2.2 生产系统

回答“如何把目标变成可运行产品”：

- 产品、交互和技术方案；
- 业务纵向切片与依赖；
- 代码、配置、数据和文档变更；
- 集成、迁移和发布候选；
- 决策、进度、阻塞和证据持久化。

### 2.3 保障系统

回答“如何证明它真的正确”：

- 阶段门禁；
- 自动化检查；
- 独立审查；
- 真实运行与真实浏览器验证；
- 需求到证据的追溯；
- 安全、数据、性能、可运维性与回滚检查。

## 3. 项目模式

启动时必须先分类，禁止所有项目套用同一流程重量。

| 模式 | 典型输入 | 调查重点 | 主要风险 |
|---|---|---|---|
| `greenfield` 新产品 | 想法、目标用户、参考产品 | 问题证据、方案探索、基础架构 | 在错误目标上快速堆功能 |
| `feature` 已有系统新增功能 | 需求、仓库、现有用户路径 | 当前行为、兼容性、边界 | 破坏既有流程和隐含规则 |
| `workflow-change` 企业流程改造 | 现有流程、角色、审批规则 | 责任、状态、权限、审计 | 把业务协调问题误写成页面 |
| `integration` 系统集成 | 两端系统、契约、数据流 | 权威源、幂等、失败恢复 | 猜测字段、重复写入、数据漂移 |
| `migration` 迁移或替换 | 旧系统、目标系统、历史数据 | 映射、校验、灰度、回滚 | 数据丢失和不可逆切换 |
| `remediation` 缺陷与质量治理 | 故障、测试、日志、影响范围 | 根因、复现、回归范围 | 只修表象或引入新回归 |

项目可以有一个主模式和最多两个辅模式。模式选择必须记录依据；如果模式变化会改变范围或风险，重新进入阶段 0。

## 4. 质量档位

### Q0：探索验证

用于证明需求或技术可行性。允许模拟非核心外围能力，但必须显式标记；不得宣称可生产使用。

最低要求：核心假设、可运行演示、已知限制、继续或停止证据。

### Q1：内部工具

用于有限内部用户。要求基本身份、权限、数据可靠性、错误处理、日志、备份和恢复。

### Q2：生产业务系统

用于真实业务。除 Q1 外，要求迁移、审计、监控、报警、容量、性能、安全、兼容、回滚和支持预案。

### Q3：企业关键系统

用于关键流程、多租户、敏感数据或明确 SLA。除 Q2 外，要求租户隔离、最小权限、灾难恢复、故障演练、依赖降级、变更审批、合规证据和责任矩阵。

质量档位只能由授权者降低。AI 可以根据风险证据建议升档，不能为了更快完成自行降档。

## 5. 自主权限契约

启动前生成 `DELIVERY_MANIFEST.yaml`，至少记录：

```yaml
project:
  name: ""
  mode: greenfield
  quality_profile: Q1
  objective: ""
  target_users: []
  in_scope: []
  out_of_scope: []

autonomy:
  reversible_product_decisions: allowed
  reversible_technical_decisions: allowed
  dependency_changes: conditional
  schema_migrations: conditional
  external_writes: denied
  production_deploy: denied
  destructive_actions: denied

budgets:
  max_delivery_cycles: 3
  max_failed_attempts_per_check: 3
  time_limit: ""
  cost_limit: ""

required_gates:
  - G0
  - G1
  - G2
  - G3
  - G4
  - G5
  - G6
  - G7
  - G8
```

### 5.1 AI 可自主决定

- 已有规范内的可逆实现细节；
- 不改变业务含义的命名、组织和局部重构；
- 与仓库既有模式一致的测试与错误处理；
- 不扩张范围的低风险 UX 细节；
- 已授权预算内的方案选择；
- 失败后可完整恢复的实验。

每项重要决定写入 `DECISIONS.md`，包含背景、候选、选择、依据、影响和回退方式。

### 5.2 必须暂停

- 不同解释会改变目标用户、业务流程、权限、计费或数据含义；
- 缺少必要来源，继续只能编造事实；
- 需要新凭证、额外权限、外部写入或超出预算；
- 涉及生产发布、真实通知、支付、删除数据或不可逆迁移且未预授权；
- 验收标准互相冲突或判卷文件疑似错误；
- 同一检查连续失败三次且没有新的证据；
- 结果低于基线并无法可靠恢复；
- 发现安全、隐私、合规或数据完整性高风险。

暂停时写 `BLOCKED.md`，继续完成不受影响的工作，不得用猜测绕过阻塞。

## 6. 端到端状态机

```text
S0 INTAKE
  -> S1 DISCOVERY
  -> S2 PRODUCT_DEFINITION
  -> S3 SOLUTION_DESIGN
  -> S4 DELIVERY_PLANNING
  -> S5 IMPLEMENTATION
  -> S6 INDEPENDENT_VERIFICATION
  -> S7 RELEASE_READINESS
  -> S8 DELIVERY
  -> S9 OUTCOME_REVIEW

任一阶段：
  -> BLOCKED（缺证据、权限或裁决）
  -> REWORK（门禁失败，回到责任阶段）
  -> STOPPED（达到止损条件）
```

只有门禁证据通过，状态才能前移。修改前置阶段的冻结结论时，必须使所有受影响的下游门禁失效并重新验证。

## 7. 阶段规格

### S0：项目建档与可执行性判断

**输入**：用户目标、可访问材料、仓库和权限。

**动作**：

1. 识别项目模式、质量档位、利益相关者和授权边界。
2. 区分业务结果、功能设想、技术手段和限制条件。
3. 检查 Agent 是否拥有代码、运行环境、日志、测试和必要连接器。
4. 给关键未知项分级：可调查、可逆默认、必须裁决。
5. 冻结预算和硬停止条件。

**产物**：`DELIVERY_MANIFEST.yaml`、`ASSUMPTIONS.md`。

**G0 放行条件**：目标、模式、质量档位、可改范围、不可做事项和暂停条件全部明确。

### S1：调查分析

**输入**：项目建档、仓库、文档、用户与业务证据。

**动作**：

1. 还原当前用户任务、业务流程、系统行为和数据流。
2. 查找现有能力、重复能力、约束、历史决策和已知失败。
3. 对新产品调查用户问题、替代方案和可用证据；对已有系统建立当前行为基线。
4. 将发现分为事实、已验证经验、假设、未知和冲突。
5. 识别不做软件也可能解决问题的方案，避免先入为主。

**产物**：`DISCOVERY.md`、当前流程或系统地图、证据索引。

**G1 放行条件**：核心问题有来源支撑；当前状态可复现；关键冲突已解决或显式阻塞；没有把假设写成事实。

### S2：产品定义

**输入**：调查证据和授权目标。

**动作**：

1. 定义目标用户、触发场景、期望结果和成功指标。
2. 写出端到端主流程、角色、状态、权限和关键业务规则。
3. 定义异常、取消、恢复、重复操作和数据生命周期。
4. 明确范围、非目标、兼容要求和待验证假设。
5. 将大目标收敛为可独立验收的业务纵向切片。

**产物**：`PRODUCT_SPEC.md`、用户流程、规则表、验收场景。

**G2 放行条件**：每个范围内能力都有用户、场景、规则和可观察结果；关键路径不存在产品语义歧义；非目标明确。

### S3：产品、交互与技术方案设计

**输入**：已冻结产品定义。

**动作**：

1. 比较可行方案，评估复用、购买、二开和自研。
2. 产品与交互设计覆盖信息架构、导航、页面、状态、反馈、错误、空状态、加载、权限差异和响应式行为。
3. 技术设计覆盖模块边界、数据模型、接口契约、一致性、幂等、缓存、权限、安全、性能、可观测性和故障恢复。
4. 涉及数据变化时设计迁移、校验、双写或灰度、回退和备份恢复。
5. 在实现前定义测试策略、黄金样本和高风险反向验证。

**产物**：`SOLUTION_DESIGN.md`、界面原型或流程图、架构决策、接口与数据契约、`TEST_STRATEGY.md`。

**G3 放行条件**：方案能覆盖产品流程；关键取舍有证据；所有高风险点都有验证与恢复办法；设计可以转化为实现任务。

### S4：交付规划与基线

**输入**：通过门禁的产品和技术设计。

**动作**：

1. 实测构建、测试、启动、数据和权限基线，不相信文档自述。
2. 按业务纵向切片拆分任务，每个切片包含界面、逻辑、数据、权限和验证。
3. 标明依赖、唯一写入方、路径白名单、共享契约和集成顺序。
4. 建立需求到设计、代码、测试和证据的追溯表。
5. 规划中断恢复、失败回滚和并行隔离。

**产物**：`BASELINE.md`、`DELIVERY_PLAN.md`、`TRACEABILITY.md`、初始 `PROGRESS.md`、`BLOCKED.md`。

**G4 放行条件**：基线有真实输出；任务可独立验证；依赖和归属明确；验收标准被冻结且不由实现者修改。

### S5：开发与集成

**输入**：获批计划、冻结规格和基线。

**动作**：

1. 按依赖逐个完成业务切片，优先形成最小可运行骨架。
2. 每次修改都运行最接近变更的检查，再运行集成检查。
3. 新发现与规格不一致时记录偏差，按影响回到对应阶段，不静默改变产品。
4. 持续更新进度、决策、阻塞、测试和实际变更证据。
5. 禁止删测试、跳过测试、放宽断言、伪造核心对象、写死结果或忽略退出码来获得假通过。

**产物**：可运行实现、测试、迁移、必要文档、构建与运行证据。

**G5 放行条件**：所有范围内切片可运行；局部和集成检查通过；基线不退化；规格偏差均有授权和记录。

### S6：独立综合验收

**输入**：发布候选、冻结规格和测试策略。

**动作**：

1. 由未参与实现的检查角色按原始目标验收，默认只读。
2. 运行功能、回归、接口、数据、权限、安全、性能和异常恢复检查。
3. 前端必须在真实浏览器验证关键任务、响应式布局、空状态、加载、错误、键盘和可访问性；截图不能替代交互验证。
4. 对报警、权限、迁移、恢复等关键机制执行一次受控的红到绿反向验证。
5. 从用户目标向下检查遗漏，从代码变更向上检查无需求扩张。

**产物**：`VERIFICATION_REPORT.md`、缺陷清单、实际命令与运行证据。

**G6 放行条件**：所有强制检查通过；无未解释的范围偏差；关键用户路径和失败路径均有证据；Checker 没有修改判卷标准。

### S7：发布就绪

**输入**：通过独立验收的候选版本。

**动作**：

1. 核对环境变量、密钥、依赖、许可证、构建物和配置差异。
2. 准备发布顺序、迁移、灰度、监控、报警、回滚和支持预案。
3. 验证备份可恢复，回滚步骤可执行，关键指标可观测。
4. 生成面向用户、运维和下一位维护者的最小必要说明。

**产物**：`RELEASE_PLAN.md`、`RUNBOOK.md`、变更说明、回滚与恢复证据。

**G7 放行条件**：发布和回退均可执行；失败会被发现；责任人和权限明确；生产操作已获授权。

### S8：交付

**输入**：发布就绪证据和发布权限。

**动作**：

- 未授权生产发布时，交付可部署候选和完整证据，不越权上线。
- 已授权时按发布计划执行，实时记录结果；异常达到阈值立即回滚。
- 交付报告区分已完成、未完成、被阻塞、未验证和后续建议。

**产物**：`DELIVERY_REPORT.md`、版本或提交标识、部署证据或候选包。

**G8 放行条件**：交付物可定位、可复现、可恢复；完成声明与证据一致；没有把计划或建议写成已上线事实。

### S9：结果观察

**输入**：真实使用、业务指标、故障和用户反馈。

**动作**：比较基线与目标，识别产品问题、体验问题、工程问题和运营问题，形成下一轮候选；不得用活跃量或功能数量替代业务结果。

**产物**：`OUTCOME_REVIEW.md`。

**放行结论**：继续扩大、调整方案、维持、回滚或停止。

## 8. 追溯协议

`TRACEABILITY.md` 至少包含：

| ID | 用户/业务结果 | 产品规则 | 设计位置 | 实现位置 | 正向测试 | 反向/异常测试 | 运行证据 | 状态 |
|---|---|---|---|---|---|---|---|---|

规则：

- 范围内需求没有实现或证据时，不得完成。
- 代码变更找不到对应需求或必要工程理由时，视为范围扩张。
- 需求、规则或接口变化时，自动标记相关下游证据过期。
- 相同结果不重复维护多份权威规格；派生文档必须指向权威源。

## 9. 持久化脊柱

每个项目使用 `.codex/delivery/` 保存执行状态：

```text
.codex/delivery/
├── DELIVERY_MANIFEST.yaml
├── STATE.json
├── ASSUMPTIONS.md
├── DISCOVERY.md
├── PRODUCT_SPEC.md
├── SOLUTION_DESIGN.md
├── TEST_STRATEGY.md
├── BASELINE.md
├── DELIVERY_PLAN.md
├── TRACEABILITY.md
├── DECISIONS.md
├── PROGRESS.md
├── BLOCKED.md
├── VERIFICATION_REPORT.md
├── RELEASE_PLAN.md
├── RUNBOOK.md
├── DELIVERY_REPORT.md
└── evidence/
```

并非每个项目都必须产生所有文件。Q0 可合并轻量产物；Q2/Q3 必须保留足以审计的独立证据。`STATE.json` 是机器状态，Markdown 是人可审阅的权威记录。

### 9.1 `STATE.json` 最小字段

```json
{
  "schema_version": 1,
  "project_mode": "feature",
  "quality_profile": "Q2",
  "current_stage": "S4_DELIVERY_PLANNING",
  "gate_status": {"G0": "passed", "G1": "passed", "G2": "passed", "G3": "passed"},
  "active_slice": null,
  "blocked_items": [],
  "failed_attempts": {},
  "invalidated_artifacts": [],
  "last_verified_at": null,
  "next_action": "establish baseline"
}
```

每次可观察动作完成后立即更新，不依赖对话记忆。新会话必须先读取 Manifest、State、Progress、Blocked 和当前阶段权威产物。

## 10. 角色与隔离

角色是职责边界，可以由独立 Agent、独立会话或有隔离上下文的独立执行轮次承担。

| 角色 | 主要责任 | 禁止事项 |
|---|---|---|
| Analyst | 调查事实、问题和现状 | 为了推进而编造证据 |
| Product Designer | 产品规则、流程和体验 | 私自扩大业务目标 |
| Architect | 技术方案和风险 | 未比较方案就锁定熟悉技术 |
| Planner | 切片、依赖、门禁和追溯 | 用水平技术层代替业务闭环 |
| Maker | 实现和自测 | 修改判卷标准或自行宣布验收 |
| Product/UX Checker | 用户任务与体验验收 | 直接代替 Maker 修复 |
| Engineering Checker | 代码、数据、接口与回归审查 | 接受没有真实输出的完成声明 |
| Security/Release Checker | 风险与发布就绪 | 越权执行生产操作 |

客观自动检查优先于 LLM 判断；需要主观判断时才使用独立 Checker。高风险项目不能由同一上下文同时扮演 Maker 和最终 Checker。

## 11. 企业级横切质量清单

根据质量档位选择，不机械全开：

- 身份、角色、资源权限、租户隔离和越权拒绝；
- 数据模型、唯一性、幂等、一致性、删除和保留策略；
- 审计记录、时间、操作者、前后值和来源；
- 输入校验、错误语义、超时、重试、降级和恢复；
- 性能基线、容量假设、慢路径和资源上限；
- 浏览器、设备、版本和接口兼容；
- 可访问性、键盘路径、文本溢出和响应式布局；
- 日志、指标、追踪、报警和健康检查；
- 备份、恢复、迁移、回滚和灾难恢复；
- 密钥、隐私、敏感数据、依赖和许可证；
- 用户文档、运维手册和支持责任。

## 12. 总控执行算法

```text
读取已有交付状态；不存在则进入 S0

循环：
  1. 读取当前阶段、权威产物、阻塞和预算
  2. 检查是否达到停止或暂停条件
  3. 只加载当前阶段所需参考规则
  4. 执行当前阶段最小可验证动作
  5. 保存产物、证据、决策和状态
  6. 运行当前阶段门禁
  7. 通过：进入下一阶段
     失败且可修复：返回责任阶段，记录失效范围
     缺权限/证据/裁决：进入 BLOCKED
     达到止损：进入 STOPPED 并如实交付

完成条件：G8 通过，或已按授权完成 S9 结果复核
```

不得为了保持循环运行而降低标准。可靠停止优先于看似完成。

## 14. Skill 验证方案

结构校验只能证明 Skill 文件合法，不能证明它能高质量交付。V0.1 实现后必须进行三个独立前向测试。

### 用例 A：已有系统新增功能

验证：是否先理解现有行为，保持兼容，完成一个端到端业务切片，并发现隐藏回归。

### 用例 B：从零内部工具

验证：是否先收敛问题和范围，完成产品与技术设计，交付真实可用界面而非静态演示。

### 用例 C：企业流程改造或系统集成

验证：是否正确处理角色、状态、权限、契约、幂等、审计和失败恢复，而不是只增加页面与接口。

每次测试必须检查：

1. 是否在关键证据不足时停下，而不是猜测；
2. 是否完整保存状态并能在新会话继续；
3. 是否存在需求到证据追溯；
4. Checker 是否发现 Maker 遗漏；
5. 是否产生假绿、越界修改或虚假完成声明；
6. 用户只在真正需要决策的地方被打断；
7. 最终产品是否能完成真实任务，而不只是通过代码测试。

## 15. V0.1 实施顺序

1. 实现 Manifest、State 和阶段路由。
2. 实现 S0-S4：先保证分析、设计和规划不会被跳过。
3. 接入现有开发执行、目标验证和 Maker-Checker 方法。
4. 实现追溯、门禁失效和阻塞协议。
5. 实现 Q0-Q2，暂不宣称覆盖 Q3。
6. 运行三个前向测试并记录失败。
7. 根据真实失败收窄或修正规则，再发布 V0.1。

## 16. 本规格的待验证问题

- 阶段产物是否过多，Q0/Q1 应如何自动合并而不丢失证据；
- 单 Agent 隔离轮次能否达到独立 Checker 的效果，何时必须使用独立 Agent；
- 如何在不同技术栈中可靠发现真实构建、测试、启动和部署命令；
- 如何判断产品与 UX 门禁已达到可交付水平，而不退化为 LLM 主观评分；
- 追溯表的维护成本是否会抵消自动化收益；
- 长周期项目如何与任务看板、CI、代码托管和生产监控同步状态；
- 哪些 Q3 控制必须由组织级政策或专业工具提供，不能写入通用 Skill。

这些问题不在文档中预设答案，应通过三个前向测试获得证据后决定。
